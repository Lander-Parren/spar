# spar cards

Small visual explanations, generated by spar, in one consistent visual language.

Status: implemented on branch `cards`. See `2026-08-21-cards-plan.md` for the build order.

## Why

spar exists to make you understand something you got wrong. Everything it produces to
that end is currently prose: the three questions, the closing review, the returning gap.
For a reader who takes in structure faster from a picture than from a paragraph, prose is
spar failing at its own job.

The requirement did not come from theory. It came from a user describing a specific
threshold: diagrams help, but only while they stay small. Too many parts, more than one
decision point, or anything that does not fit in a single glance, and the benefit
reverses. Several small pictures beat one large one.

That threshold is the whole design. It is not advice in a prompt, it is a limit the CLI
enforces.

## What it is

One command that renders a single-idea card to a self-contained HTML file.

```sh
spar card --layout chain \
  --title "Predict before you're told" \
  --subtitle "The gap between your guess and what was true is worth writing down." \
  --step "you:You predict" --step "agent:AI implements" \
  --step "you:You compare" --step "result:Gap logged" \
  --loop "sets the next level" \
  --bullet "You take a position|before the answer exists" \
  --close "Without predicting first, reviewing finished code teaches you almost nothing."
```

Writes `~/.spar/cards/<slug>.html`, prints the path, opens it unless `--no-open`.

## Layouts and their limits

Four layouts, chosen because they cover the reference set the requirement came from: a
chain, a fan-out, a sequence, and a comparison.

| Layout | Shape | Limit |
|---|---|---|
| `chain` | steps left to right, optional feedback arc via `--loop` | 2 to 5 steps |
| `fanout` | one source to several receivers, optional `--via` label on the bar | 2 to 4 receivers |
| `sequence` | two actors, numbered messages, each with a direction | 2 to 4 messages |
| `compare` | two cards side by side, title and body each | exactly 2 |

### Flags

Shared by every layout:

| Flag | Meaning |
|---|---|
| `--layout` | one of the four above, required |
| `--title` | the headline, required |
| `--subtitle` | one line under it, required |
| `--bullet` | `visible\|muted`, repeatable, at most 3 |
| `--close` | the muted closing line, optional |
| `--no-open` | write the file without opening it |

Per layout:

| Layout | Flags |
|---|---|
| `chain` | `--step "role:label"` repeated 2 to 5 times; `--loop "label"` for the feedback arc |
| `fanout` | `--from "role:label"` once; `--to "role:label"` repeated 2 to 4 times; `--via "label"` for the bar |
| `sequence` | `--actor "role:label"` exactly twice; `--msg "dir:label"` repeated 2 to 4 times, where `dir` is `>` from the first actor to the second or `<` for the reverse |
| `compare` | `--card-pane "role:title\|body"` exactly twice |

The pane flag is `--card-pane` rather than `--card`, because `spar card --card` reads
like a mistake.

The output file is named from a slug of the title, so re-rendering the same card replaces
it rather than accumulating copies. `--out <path>` overrides.

Cards do not depend on a tracked project. `spar card` works anywhere, including on a fresh
install with no config, because explaining something is not gated the way writing code is.

**Exceeding a limit is an error, not a warning.** `spar card` exits 1 and names the limit
it hit. This is the same move as the level 2 skeleton check: a constraint that lives only
in a prompt drifts, and the agent has a mild incentive to drift here because a bigger
card is less work than deciding what to leave out. A constraint that lives in code does
not drift.

## Colour encodes role, not sequence

A step is written `role:label`. The role before the colon selects a palette slot; a step
with no colon gets the neutral slot.

**At most three distinct roles per card.** A fourth is an error. Rainbow-by-step is the
most common way a small diagram stops being readable, and this makes it impossible rather
than discouraged.

Roles are free-form strings, so the same word means the same colour across a whole set of
cards: `you` is always one colour, `agent` always another. Slots are assigned in order of
first appearance, which keeps a card stable when it is re-rendered.

The `visible|muted` split on a bullet matches the two-tone reading of the reference set.
The muted half is optional.

Bullets take the role colour for their dot, in the order the roles appear in the diagram.
A card with fewer roles than bullets repeats from the start. That is what ties the list to
the picture in the reference set rather than leaving the dots decorative.

## Themes

`cards.theme` in `~/.spar/config.json`.

- `neon` (default): dark ground, outlined boxes with a glow on the stroke, vivid role
  colours, one loose arc with an informal label where a card has a feedback element.
- `plain`: flat, muted, adapts to the viewer's light or dark preference.

Themes are palettes and stroke treatments only. They never change the layout maths, so a
card carries the same information in either theme. The README states the default and the
one config line that changes it.

## Where spar asks for a card itself

Two moments, both about understanding rather than about friction:

1. **After `spar done`.** The closing instructions gain a line: when a difference is a
   misconception with more than a couple of moving parts, render it as a `compare` card
   before writing the gap.
2. **When a gap comes back.** If the user cannot answer, the injected context asks for a
   card explaining the concept rather than a paragraph.

Everywhere else the agent may use it freely. The skill documents the bar: reach for a
card when an explanation has three or more moving parts and would otherwise be a
paragraph. Below that, prose is better and faster.

## Files

```
src/core/card.ts          card model, parsing role:label and visible|muted, limit checks
src/core/card-layout.ts   pure geometry per layout: boxes, arrows, label positions
src/render/card.ts        layout result to SVG and HTML
src/render/card-theme.ts  the two palettes
src/commands/card.ts      the CLI surface
templates/card.html       the shell: title, subtitle, slot for the SVG, bullets, close
test/card.test.ts         limits and parsing
test/card-layout.test.ts  geometry
```

`card-layout.ts` returns coordinates and never touches strings or colour. That split is
what makes the geometry testable.

## Testing

The usual: limits rejected, roles capped at three, parsing of both compact syntaxes, no
unreplaced placeholders, no network reference in the output, one `<svg>` per card.

And one kind of test that earns its place here more than usual: **geometry**.

Diagrams fail in a small number of predictable ways. Labels overlap, an arrow crosses a
box it has nothing to do with, text leaves the viewBox. Because spar computes the
coordinates rather than asking a model to imagine them, every one of those becomes an
assertion over the layout result:

- no two boxes overlap
- every box lies inside the viewBox with a margin
- every label fits inside its own box at the theme's font size
- no arrow segment passes through a box that is not its source or target
- the viewBox is tight: content bottom plus a fixed margin

Run for each layout at its minimum and maximum size, which is where packing breaks.

## Not in this design

No animation, no interactivity, no stepper. A card is one still picture of one idea; if
something needs several, that is several cards with prose between them, which is the point
of the size limit in the first place.

No image export. The output is HTML, and a browser can already do the rest.

No layout beyond the four. A fifth is a separate decision, made when a real explanation
turns out not to fit any of them.
