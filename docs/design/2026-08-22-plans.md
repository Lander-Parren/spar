# spar plans

A ticket becomes steps, and each step is gated on its own.

Status: design, not yet implemented.

## Why

The third question is the one that carries the tool: *where will this go wrong?*

It is answerable for "add the cancel endpoint". It is not answerable for "implement order
cancellation with refunds and audit logging", where any answer is a guess and the
calibration figure stops measuring anything.

One ticket produces one prediction. Five steps produce five, each small enough to be
genuinely wrong about. Breaking the work up is not project management here, it is
**prediction granularity**.

Two things follow that are worth as much as the granularity itself.

**The task boundary stops being a guess.** Today it is inferred from silence: thirty
minutes without movement and the gate re-arms. With a list of steps, spar knows exactly
where step four ends and step five begins.

**The prediction survives the session.** Today level and prediction live in
`~/.spar/state/<session>.json`, so closing the terminal loses them and the next session
starts over. On a ticket that runs for three days that is precisely backwards. Attached to
a step, the prediction is still there tomorrow.

## What spar does not do

It does not plan. That already exists three times over: superpowers `writing-plans`, OMC
`plan` and `ralplan`, and whatever the agent does in conversation. spar has no opinion
about how the work is broken up and no connection to any issue tracker.

The division: your MCP fetches the ticket, your planner breaks it into steps, and spar
decides how much of each step is yours.

## Storage

`<project>/.spar/plan.json`, one active plan per tracked project. `spar setup` adds
`.spar/` to the project's `.gitignore`, creating that file if the project has none, and
does nothing when the entry is already there. Running setup twice leaves one line.

```json
{
  "title": "PROJ-123 cancel and refund an order",
  "created": "2026-08-22T10:00:00Z",
  "current": 1,
  "steps": [
    {
      "title": "Add a cancelled status to the order model",
      "status": "done",
      "concepts": ["modelling state transitions"],
      "level": 1,
      "predicted": true,
      "testWritten": true
    },
    { "title": "Refund before the write, roll back on failure", "status": "active" },
    { "title": "Refuse cancelling a shipped order", "status": "todo" }
  ]
}
```

`status` is `todo`, `active` or `done`. Exactly one step is `active` while the plan is
unfinished, and `current` is its zero-based index into `steps`, kept in sync so a reader
does not have to scan for the active one.

`spar plan` needs a tracked project, since it writes inside one. Run outside every
configured project it says so and exits 1 rather than creating a directory somewhere
arbitrary.

**The plan lives with the project, the gap log lives with you.** What you do not yet
understand about transaction boundaries is nobody's business and stays in `~/.spar/`. How
a ticket was broken up is about the work, so it belongs beside the code it is about.

## Commands

| Command | What it does |
|---|---|
| `spar plan --title "..." --step "..." --step "..."` | Create a plan. Repeat `--step` per step. |
| `spar plan --from <file.md>` | Same, reading step titles out of a markdown plan. |
| `spar plan` | Show the plan and which step is active. |
| `spar step done` | Mark the active step done and activate the next. |
| `spar plan --clear` | Discard the plan and fall back to the idle boundary. |

`spar step done` with no plan is an error, not a silent no-op: exit 1 saying there is no
plan and pointing at `spar plan`. Finishing a step you never started is the kind of
confusion worth naming.

Marking the last step done completes the plan. The command says so, and says the gate has
returned to the idle boundary, so nobody is left wondering why it stopped firing per step.

`--from` reads `## Task ...` and `### Task ...` headings, which is what superpowers
`writing-plans` and the OMC planners produce. Anything else is not parsed; use `--step`.
The flag is a parser in front of the same entrance, not a second way in.

Creating a plan while an unfinished one exists requires `--replace`, and the command
prints how many steps were discarded. Losing a plan you were halfway through by accident
is not a mistake worth allowing.

Concepts are not passed on the command line. They attach to the active step when the
agent names them for `spar suggest-level`, exactly as they do today.

## The step is the task

While a plan is active, the active step is the task, and the idle timer is off. The gate
fires once per step rather than once per stretch of silence.

Level, prediction and the test flag are read from and written to the active step rather
than to session state. One accessor decides which of the two is in play, so the hooks do
not each carry the branch:

```
taskState(sessionId, cwd) -> { level, predicted, testWritten, ... }
```

With no plan, it reads session state and everything behaves exactly as it does now. That
fallback is what keeps this additive: a user who never runs `spar plan` sees no change.

`rush` stays session state in both cases. It says "not now, I am in a hurry", which is
about this sitting rather than about the step, and a rush that outlived the terminal would
be a rush you forgot you set.

When every step is `done` the plan is complete, `spar plan` says so, and the gate returns
to the idle boundary.

## A level per step

When a step becomes active, `suggest-level` runs over that step's concepts and the
suggestion is stored on the step.

This is where the granularity pays for itself. Over five steps the friction lands on the
two that touch concepts you have open gaps on, and stays out of the way on the three that
do not. Averaged over a whole ticket that distinction disappears, which is why a big task
gets a level that is wrong for most of it.

## Finishing a step

`spar step done` applies the same bar as the handover. At level 2 or 3 it refuses while
no test has been written for that step, and names the reason.

A tick box that can be ticked regardless is a tick box that means nothing. The step is not
done because you say so; it is done when it meets what the level asked for.

`spar rush` still degrades a step to level 0, which is the escape hatch, and it is
counted the way it already is.

## Files

```
src/core/plan.ts          the plan model: read, write, advance, parse a markdown plan
src/core/task-state.ts    the accessor: active step when there is a plan, session otherwise
src/commands/plan.ts      spar plan
src/commands/step.ts      spar step done
test/plan.test.ts         model, parsing, advancing, the replace guard
test/task-state.test.ts   which of the two sources is in play, and that it round-trips
```

`src/hooks/*` change only by reading through `task-state.ts` instead of `store.ts`.

## Testing

Beyond the model and the parser:

- With no plan, every existing hook behaves exactly as before. This is the test that keeps
  the feature additive, and it should run the same assertions the current gate tests use.
- A prediction recorded against a step is still there when the session id changes, which
  is the persistence claim stated out loud.
- `spar step done` refuses at level 2 and 3 without a test, and accepts once there is one.
- Creating over an unfinished plan refuses without `--replace`.
- A markdown plan with nine `### Task` headings yields nine steps, and a file with none
  yields a readable error rather than an empty plan.
- `.spar/` ends up in the project's `.gitignore` after `spar setup`, and setup does not
  add it twice.

## Not in this design

No issue tracker integration of any kind. The agent can already read a ticket, and binding
a public package to one vendor buys nothing.

No planning. spar takes steps and does not judge them.

No multiple plans, no branches, no dependencies between steps. A flat list, in order, one
at a time. If a ticket needs more structure than that, the planner that produced it is the
place for it.

No sharing. The plan is gitignored by default. Committing it is a decision a team can make
on its own; spar does not make it for them.
